## Модуль 3. Многопоточность и асинхронность

**Поток (Thread)** — наименьшая единица выполнения внутри процесса.
**Процесс (Process)** — изолированная среда выполнения приложения.

**Асинхронность** — механизм, позволяющий *не блокировать поток* во время длительных операций (чаще всего ввода-вывода).

---

## Ключевые концепции

* **Thread / ThreadPool** — низкоуровневое управление потоками
* **Task / Task<T>** — высокоуровневая абстракция для асинхронной работы
* **async / await** — синтаксический сахар для работы с Task

---

## CPU-bound vs I/O-bound операции

### 🔹 I/O-bound операции

Операции, ограниченные скоростью внешних ресурсов:

* сеть (HTTP-запросы)
* файловая система
* база данных
* API

📌 Особенности:

* Поток **ждёт** завершения операции
* CPU почти не загружен
* Главная задача — *не блокировать поток*

✅ Рекомендуемый подход:

```csharp
public async Task<string> GetDataAsync()
{
    var result = await httpClient.GetStringAsync("https://example.com");
    return result;
}
```

✔ Используем `async/await`
✔ Поток возвращается в пул, пока идёт ожидание

---

### 🔹 CPU-bound операции

Операции, ограниченные вычислительными ресурсами:

* математические расчёты
* обработка изображений
* шифрование
* работа с большими массивами данных

📌 Особенности:

* Активно загружают CPU
* Поток занят всё время выполнения

✅ Рекомендуемый подход:

```csharp
public Task<int> CalculateAsync()
{
    return Task.Run(() =>
    {
        // тяжелые вычисления
        return Enumerable.Range(1, 1_000_000).Sum();
    });
}
```

✔ Используем `Task.Run()` для выноса в ThreadPool
✔ Позволяет не блокировать UI / основной поток

---

## ❗ Ключевое различие

| Характеристика    | I/O-bound         | CPU-bound             |
| ----------------- | ----------------- | --------------------- |
| Узкое место       | Внешние ресурсы   | Процессор             |
| Использование CPU | Низкое            | Высокое               |
| async/await       | ✅ Да              | ⚠️ Не решает проблему |
| Task.Run          | ❌ Обычно не нужен | ✅ Да                  |

## Управление потоками и процессами

### 🔹 Могу ли я контролировать создание потоков?

✅ Да, но с ограничениями:

### 1. Высокоуровневый способ (рекомендуется)

```csharp
Task.Run(() => DoWork());
```

* Использует **ThreadPool**
* Не контролируешь конкретный поток
* Оптимально в 90% случаев

---

### 2. Явное создание потока

```csharp
var thread = new Thread(() => DoWork());
thread.Start();
```

📌 Когда использовать:

* нужен полный контроль
* долгоживущие задачи
* специфическая настройка (приоритет, STA и т.д.)

⚠️ Минусы:

* дорого по ресурсам
* нет управления пулом
* легко создать утечки ресурсов

---

### 3. ThreadPool (низкоуровневый доступ)

```csharp
ThreadPool.QueueUserWorkItem(_ => DoWork());
```

✔ Быстро
✔ Переиспользование потоков
❌ Меньше контроля

---

## 🔹 Управление процессами

Да, ты можешь создавать и контролировать **процессы**:

```csharp
using System.Diagnostics;

Process.Start("notepad.exe");
```

📌 Возможности:

* запуск внешних программ
* управление жизненным циклом
* получение stdout/stderr

---

## 💡 Практические рекомендации

* I/O-bound → всегда `async/await`
* CPU-bound → `Task.Run()` или Parallel API
* Не создавай `Thread` вручную без необходимости
* Не оборачивай I/O в `Task.Run()` (антипаттерн)
* Используй `Parallel.For`, если задача легко параллелится

---

## 🚫 Частые ошибки

❌ Блокировка async-кода:

```csharp
var result = GetDataAsync().Result; // deadlock
```

❌ Неправильное использование Task.Run:

```csharp
await Task.Run(() => httpClient.GetStringAsync(url)); // лишнее
```

## 🔹 Как реально выполняются I/O-bound операции

Когда ты пишешь:

```csharp
await httpClient.GetStringAsync(url);
```

происходит следующее:

### 1. На уровне .NET

* Создаётся асинхронная операция (`Task`)
* Поток **освобождается** (не блокируется)

---

### 2. Переход к ОС

Дальше .NET использует механизмы ОС:

* Windows → **I/O Completion Ports (IOCP)**
* Linux → **epoll / async I/O**
* macOS → **kqueue**

📌 Вот здесь уже задействуется **ядро ОС**

---

### 3. Работа ядра ОС

ОС:

* регистрирует операцию (например, сетевой запрос или чтение файла)
* передаёт её драйверам / сетевому стеку
* **не держит пользовательский поток занятым**

➡️ То есть операция реально выполняется вне твоего managed-потока

---

### 4. Завершение операции

Когда данные готовы:

* ядро ОС сигнализирует (completion event)
* .NET получает уведомление
* задача (`Task`) помечается как завершённая
* continuation (`await`) продолжает выполнение

---

## 🔹 Важный вывод

✅ **I/O-bound операция не "выполняется потоком" в классическом смысле**
✅ Она:

* регистрируется в ОС
* выполняется асинхронно на уровне ядра/драйверов
* возвращает результат через callback/событие

---

## 🔹 Почему это важно

Это объясняет, почему:

✔ `async/await` не создаёт новые потоки
✔ масштабируемость высокая (тысячи запросов ≠ тысячи потоков)
✔ CPU почти не используется

---

## 🔹 Контраст с CPU-bound

```csharp
Task.Run(() => Compute());
```

Здесь:

* создаётся/берётся поток из ThreadPool
* код реально выполняется на CPU
* ядро ОС просто планирует поток

---

## 🔹 Упрощённая схема

```
I/O-bound:
.NET → ОС (ядро) → устройство/сеть → сигнал → .NET

CPU-bound:
.NET → ThreadPool → CPU → результат
```

---

## 🔹 Тонкость (часто спрашивают на собеседованиях)

❗ Не весь I/O “магически async”

Если API **не поддерживает настоящую асинхронность**, то:

```csharp
await Task.Run(() => File.ReadAllText(path));
```

➡️ это уже:

* обычный блокирующий I/O
* просто завернутый в поток

📌 То есть:

* **не ядро управляет асинхронностью**
* ты просто вынес блокировку в другой поток

---

## Итог

* Да, **ядро ОС участвует в I/O-bound операциях**
* Но:

  * .NET только *инициирует* операцию
  * ОС выполняет её асинхронно
  * поток освобождается до завершения
