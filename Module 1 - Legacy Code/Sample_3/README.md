# Проект Sample_3 — Рефакторинг через Wrap Method

## Назначение

Учебный проект, демонстрирующий приём **Wrap Method** (оборачивание метода) при работе с legacy-кодом. Показывает, как добавить новую функциональность (проверка директории, логирование) вокруг существующего метода, не изменяя его.

## Структура проекта

| Файл | Назначение |
|------|-----------|
| `LegacyFileWriter.cs` | Legacy-класс с методом `Write`, который пишет текст в файл |
| `SafeFileWriter.cs` | Обёртка: вызывает legacy-метод, добавляя проверки и логирование |
| `Program.cs` | Демонстрация: запись файла через legacy-класс и через обёртку |

Пространства имён: `Sample_3.Legacy` и `Sample_3.Refactored`.

## Что делает код

`LegacyFileWriter.Write(path, content)` — единственная операция: `File.WriteAllText(path, content)`. Не проверяет существование директории, не логирует, не обрабатывает ошибки.

`SafeFileWriter` — обёртка над legacy-классом:

1. `EnsureDirectoryExists(path)` — определяет директорию файла; если путь без директории — использует текущую рабочую директорию; создаёт отсутствующую папку через `Directory.CreateDirectory`.
2. `Log("Запись в файл: ...")` — логирование **до** вызова.
3. `_legacyWriter.Write(path, content)` — вызов неизменённого legacy-кода.
4. `Log("Файл успешно записан: ...")` — логирование **после**.

Демонстрация в `Program.cs` пишет два файла: `test_legacy_writer.txt` и `test_safety_writer.txt`.

## Зачем используется Wrap Method

Legacy-метод `Write`:

- прост, но небезопасен: падает, если директория отсутствует;
- не оставляет следов выполнения;
- менять его рискованно — он может использоваться в других местах.

Wrap Method позволяет:

- добавить поведение **до** и **после** старого вызова, не трогая его тело;
- сохранить сигнатуру и семантику исходной операции;
- изолировать новую логику в отдельном классе и тестировать её независимо;
- при необходимости легко откатить изменения — достаточно перестать использовать обёртку.

## Полезная теория

**Wrap Method** (М. Фаулер, «Рефакторинг») — техника, при которой существующий метод переименовывается, а под прежним именем создаётся новый метод-обёртка. Обёртка выполняет дополнительную логику до/после делегирования старому методу. Внешний API не меняется.

**Отличие от смежных приёмов:**

| Приём | Что делает |
|-------|-----------|
| **Wrap Method** | Добавляет поведение вокруг существующего метода, не меняя его тело |
| **Sprout Method** | Добавляет новый метод, вызывающий старый как строительный блок |
| **Extract Method** | Выносит фрагмент **из** существующего метода (изменяет его) |
| **Decorator** | Оборачивает объект, реализуя тот же интерфейс; допускает цепочку обёрток |

**Когда применять Wrap Method:**

- нужно добавить сквозную функциональность (логирование, проверки, метрики, транзакции);
- старый код стабилен и покрыт тестами;
- изменение тела метода рискованно или запрещено регламентом.

**Когда не применять:**

- если функциональность логически принадлежит самому методу и метод тривиален — проще изменить его напрямую;
- если обёрток становится много и они дублируют проверки — уместнее аспектно-ориентированный подход или паттерн Decorator с единым интерфейсом.

**Признаки качественного результата:**

- legacy-класс не изменён;
- обёртка делегирует вызов, а не копирует логику записи;
- дополнительная логика вынесена в приватные методы (`EnsureDirectoryExists`, `Log`);
- обёртка имеет конструктор с внедрением зависимости (testability);
- поведение обёртки описано через «до / вызов / после».

**Замечание по смыслу техники:** в классическом Wrap Method старый метод **переименовывается** (например, `Write` → `WriteInternal`), а под старым именем появляется обёртка. В данном проекте legacy-класс оставлен как есть, а обёртка реализована отдельным классом — это ближе к **Sprout Class / Decorator**, чем к строгому Wrap Method. Для учебной демонстрации допустимо, но на занятии стоит явно проговорить это различие.

## Замечания по текущей реализации (для дальнейшего улучшения)

- `LegacyFileWriter` создаётся в конструкторе по умолчанию; внедрение через второй конструктор есть, но не используется — в `Program.cs` уместно показать внедрение зависимости.
- `Log` пишет в `Console` — для реального логирования стоит абстрагировать (интерфейс `ILogger`), иначе обёртку сложно тестировать.
- `EnsureDirectoryExists` использует `dir!` — подавление предупреждения компилятора. Лучше явно обработать `null` (например, через `?? throw` или проверку), чтобы не маскировать ошибку.
- Отсутствует обработка исключений: сообщение «Файл успешно записан» выводится только при успехе, но при ошибке логирования «после» не будет — стоит предусмотреть `try/finally` или логирование ошибки.
- Порядок «создать директорию → залогировать → записать» корректен, но при сбое записи лог «успешно записан» не выведется — это ожидаемо, однако явная обработка ошибок сделала бы поведение предсказуемым.
- Имена файлов в `Program.cs` различаются (`test_legacy_writer.txt` / `test_safety_writer.txt`) — для наглядного сравнения удобнее один и тот же путь.

## Сборка и запуск

Требуется .NET SDK с поддержкой C# (top-level statements в `Program.cs`).

```
dotnet run
```

Ожидаемый вывод (при отсутствии директорий в пути):

```
[LOG] Запись в файл: test_safety_writer.txt
[LOG] Файл успешно записан: test_safety_writer.txt
```

Файлы `test_legacy_writer.txt` и `test_safety_writer.txt` появятся в текущей рабочей директории. При указании пути с несуществующей папкой legacy-версия выбросит исключение, а обёртка создаст директорию и выполнит запись.
