# Проект Sample_1 — Рефакторинг «Метод-монстр»

## Назначение

Учебный проект, демонстрирующий рефакторинг антипаттерна «Метод-монстр» (Long Method / God Method) на примере класса генерации текстового отчёта. Содержит два варианта реализации: исходный (legacy) и отрефакторенный, а также точку входа для сравнения результатов их работы.

## Структура проекта

| Файл | Назначение |
|------|-----------|
| `ReportGenerator.cs` | Legacy-версия с методом-монстром `GenerateReport` |
| `RefactoredReportGenerator.cs` | Отрефакторенная версия, разбитая на мелкие методы |
| `Program.cs` | Демонстрация: вывод результата обеих версий |

Пространства имён: `Sample_1.Legacy` и `Sample_1.Refactor`.

## Что делает код

`GenerateReport(List<string> data)` формирует строковый отчёт:

1. Заголовок `"Отчет:"` и разделитель `"===================="`.
2. Тело — по строке `"Элемент: {item}"` на каждый элемент.
3. Разделитель, итог `"Всего элементов: {Count}"`.
4. При количестве элементов > 10 — предупреждение `"ВНИМАНИЕ: Большой объем данных!"`.

Обе версии возвращают идентичный результат (с точностью до завершающих переводов строк).

## Проблемы legacy-версии

Метод `GenerateReport` нарушает принцип единственной ответственности (SRP):

- Смешаны форматирование заголовка, тела и подвала.
- Бизнес-правило (`Count > 10`) встроено в код формирования строки.
- Множественная конкатенация строк через `+=` в цикле — неэффективно по памяти (квадратичная сложность при больших объёмах).
- Магические литералы (разделитель, порог 10) не выделены.
- Метод сложно тестировать по частям и переиспользовать.

## Что сделано при рефакторинге

Метод разбит по зонам ответственности:

- `CreateHeader()` — формирование шапки.
- `AppendBody(data)` — формирование тела через `string.Join` + LINQ `Select`.
- `AppendFooter(data)` — разделитель, итог, предупреждение.
- `IsDataLarge(data)` — выделенное бизнес-правило.

`GenerateReport` превращён в композицию вызовов, читаемую как оглавление отчёта.

## Полезная теория

**Метод-монстр (Long Method)** — метод, выполняющий несколько разнородных задач. Признаки: десятки строк, несколько уровней вложенности, комментарии-разделители внутри тела, несколько причин для изменения.

**Правила рефакторинга длинных методов:**

1. **Extract Method** — вынести логические блоки в отдельные методы с говорящими именами.
2. **Decompose Conditional** — вынести сложные условия в предикатные методы (`IsDataLarge`).
3. **Replace Magic Number with Named Constant** — порог `10` уместно вынести в константу.
4. **Compose Method** — итоговый метод должен читаться как последовательность шагов, без деталей реализации.

**Признаки качественного результата:**

- Каждый метод отвечает на один вопрос («что делает?»), а не «как».
- Имена методов отражают намерение, а не механику.
- Бизнес-правила локализованы и легко находятся поиском.
- Отдельные части можно покрыть юнит-тестами независимо.

**Замечания по текущей отрефакторенной версии (для дальнейшего улучшения):**

- `AppendBody` и `AppendFooter` — не «append», а «build»/«format»: они возвращают новые строки, а не дописывают в переданный буфер. Имена вводят в заблуждение.
- При пустом списке `AppendBody` вернёт `"\n"` (артефакт `string.Join` + `"\n"`), тогда как legacy-версия не добавит пустую строку. Поведение не полностью эквивалентно.
- Класс помечен `internal`, тогда как legacy-версия — `public`; для симметрии API стоит выровнять.
- Строковые литералы (разделитель, тексты сообщений) дублируются и не вынесены в константы.
- `string` как тип результата отчёта — упрощение; в реальном коде уместнее модель отчёта (заголовок, строки, метаданные) с отдельным рендерером.

## Сборка и запуск

Требуется .NET SDK с поддержкой C# (используются top-level statements в `Program.cs`).

```
dotnet run
```

Ожидаемый вывод: два блока — «Было» и «Стало» — с идентичным содержимым отчёта.
